## Summary

Changes since the previous audit are a dependency refresh (BouncyCastle 2.6.2 → 2.7.0,
MessagePack 3.1.8 → 3.1.12 for a published advisory, Roslyn 4.14 → 5.9, RestSharp
112 → 114, and others), a `KeyPair`/`Account` seed-handling rework forced by BouncyCastle 2.7,
a hardening of the ARC32/ARC56 client generator against contract descriptions that could break
out of a comment into generated code, a LogicSig-args msgpack decode fix, and a new PR-gating CI
workflow. Nothing in this range sends key material anywhere new, adds network surface, or weakens
signing. The BouncyCastle bump was done safely: the Falcon golden vectors (the `RISK-016`/`RISK-017`
gate) pass on 2.7.0, and the one behavioural break (deterministic `Account(seed)`) was caught and
fixed loudly rather than shipped silently. `dotnet list package --vulnerable` reports no
vulnerable packages for the SDK or the generator CLI. Two findings from the previous audit (N1
buffer wiping, N2 test-key comment) are still open. Verdict: as of this commit the SDK does not
put user private keys at risk beyond the registered inherent and residual risks.

## Findings

### G1 — Client generator: contract descriptions could escape a comment and inject code into generated clients — fixed
- **Severity**: Medium (before fix; the generator output is compiled into consumers' apps)
- **Confidence**: Confirmed (read the pre- and post-change code; the injection mechanism is a
  plain string replace)
- **Status**: New and Resolved in this range (commit `7922b93`; see
  `StringExtensions.cs:10-28`)
- **Location**: `ClientGenerator/Extensions/StringExtensions.cs:10-28`,
  `ABI/ARC4/MethodDescription.cs:195-197`, call sites in `ARC32/AppDescription.cs`,
  `ARC32/StorageSection.cs`, `ARC56/ClientGeneratorARC56.cs`.
- **Description**: Previously the generator wrote contract/method descriptions into `///` and `//`
  comments using `Replace("\n", "\n///")`. That handled `\n` but not `\r`, nor the Unicode line
  terminators the C# lexer also treats as the end of a `//` comment (NEL U+0085, LS U+2028,
  PS U+2029). A description containing one of those followed by C# text would have emitted that
  text as live code in the generated client. The new `ToDocCommentText`/`ToLineCommentText`
  normalise every line terminator and prefix each resulting line, and `Sanitize` now also
  neutralises NEL/LS/PS. This closes the realistic variant of the `RISK-008` "tampered ARC56
  spec" vector.
- **Failure scenario (pre-fix)**: a developer generates a client from an ARC56 JSON whose
  `description` contains `"  static readonly ... = Exfiltrate();"`; the text compiles into the
  client. Needs a malicious or tampered spec plus the developer not reading the generated file.
- **Residual**: other spec-derived strings that are emitted as identifiers or string literals (method
  names, argument names, struct/field names) were not re-audited this cycle. Plausible, not
  confirmed, concern; the generator already applies PascalCase/sanitising helpers to most of them.
- **Recommendation**: Add a generator test that feeds NEL/LS/PS/`*/`/`</summary>` into every
  description field and compiles the output; audit identifier/literal emission paths next cycle.
  Keep documenting that ARC56 specs are trusted input (`RISK-008`).

### K1 — BouncyCastle 2.7 silently ignored `FixedSecureRandom`; `Account(seed)` rework — fixed, with minor residual copies
- **Severity**: High in the counterfactual (silent random keys instead of the requested
  deterministic one); Informational as shipped
- **Confidence**: Confirmed for the current code; Plausible for the pre-fix failure (taken from
  the commit comment in `KeyPair.cs:40-41`, not reproduced)
- **Status**: New and Resolved in this range (`e669f90`..`13228ed`)
- **Location**: `Crypto/KeyPair.cs:24-54`, `Algod/Model/Account.cs:80-111`,
  `Crypto/FixedSecureRandom.cs:5`.
- **Description**: `new Account(byte[] seed)` used to feed the seed through `FixedSecureRandom`
  into BC key generation. BC 2.7's Ed25519 generator does not reliably consume that source, so
  upgrading without a fix would have made `Account(seed)` return a random, unrecoverable key.
  The fix derives the key directly (`new KeyPair(privateKeyBytes)`), validates length (32 or
  64), and for the 64-byte kmd form rejects a mismatched public half instead of ignoring it.
  `FixedSecureRandom` is `[Obsolete]` and `KeyPair(SecureRandom)` throws if given one. `KeyPair`
  now clones the caller's buffer, so `Dispose()` no longer wipes (or aliases) the caller's array.
  `AsymmetricCipherKeyPair` is now built as `(public, private)`, which matches BC's
  constructor order; the earlier call passed them in the opposite order (Confirmed in the diff;
  impact of the old order was not investigated).
- **Residual (Low)**: `SeedToPrivateKey` (`Account.cs:92-110`) creates an intermediate 32-byte
  `privateKey` array and, on the 64-byte path, a temporary `Ed25519PrivateKeyParameters`; neither is
  cleared. `KeyPair` then clones the first. The caller's own `seed` array is the caller's to wipe.
  Same best-effort class as `RISK-001`.
- **Recommendation**: Clear the intermediate `privateKey` after the `KeyPair` constructor returns
  (e.g. via a small helper). Add a release note that `Account(byte[])` accepts 64 bytes and
  that `FixedSecureRandom` is obsolete, since callers who relied on the old (now throwing)
  behaviour will see an exception.

### C1 — CI/release pipeline: PR gate added; third-party actions pinned by tag, AlgoKit unpinned
- **Severity**: Low
- **Confidence**: Confirmed (read both workflow files in the diff; not executed)
- **Status**: New
- **Location**: `.github/workflows/build-and-test.yml`, `.github/workflows/publish-nuget.yml`
- **Description**: Positive: PRs now run the same build and test gate as releases;
  `build-and-test.yml` is `permissions: contents: read`; the nupkg artefact is uploaded only on
  tag or manual dispatch with `if-no-files-found: error`; publishing continues to use nuget.org
  Trusted Publishing (no long-lived secret). Weaker points: actions are referenced by mutable
  tag (`actions/checkout@v4`, `setup-dotnet@v4`, `upload-artifact@v4`), and `pipx install
  algokit` is unpinned and runs before the LocalNet tests in the same job that later builds the
  release packages, so a compromised `algokit` release could influence a package that is then
  published. I did not confirm how `publish` consumes the artefact or its permissions beyond the
  diff, so the exposure of the OIDC token to the build job is Plausible, not Confirmed (in the
  diff it sits in the separate `publish` job).
- **Recommendation**: Pin actions to commit SHAs; pin `algokit` to a version; keep the build
  job's token read-only (already so) and keep `id-token: write` confined to the `publish` job.

### R1 — Gossip DNS transaction ID and relay selection still use `System.Random`
- **Severity**: Informational
- **Confidence**: Confirmed
- **Status**: Recurring (`AUDIT-2026-07-16c.md` G1 follow-up notes)
- **Location**: `Gossip/DnsSrvResolver.cs:169`, `Gossip/GossipHttpClient.cs:21`
- **Description**: A predictable 16-bit DNS ID offers little protection against spoofing,
  but the lookup is only used to discover relays and no key material is carried over this
  channel. Not in the key or signing path.
- **Recommendation**: Switch to `RandomNumberGenerator` when next touching the file.
