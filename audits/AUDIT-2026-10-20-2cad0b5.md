# Security Audit — dotnet-algorand-sdk — 2026-10-20

Audited commit: `2cad0b5df662f201358255fa93aba206fb2c47c4` (branch `master`)
Auditor: AI agent (Claude) per `audits/AUDITS-INSTRUCTIONS.md`
Previous audit: `audits/AUDIT-2026-10-19-13228ed.md` (commit `13228ed`)

## Summary

Since the previous audit, three commits landed: the NuGet refresh merge (#9), the remediation of the
previous audit's findings (#10), and a version bump to 5.0.3. The remediations are present and correct as
read: the `Account(seed)` and Falcon transient buffers are now wiped, GitHub Actions are pinned to commit
SHAs, `algokit` is pinned, the gossip DNS ID uses a CSPRNG, and hostile-description regression tests exist.
Nothing in this range sends key material anywhere, adds network surface, or weakens signing. No package
the SDK or generator CLI references has a known vulnerability. **One new, confirmed finding:** the
previous audit left the generator's *identifier and string-literal* emission paths unverified; this audit
verified them by running the generator on hostile specs, and three spec-derived strings (an ARC56
argument name, an ARC56 event name, and the contract name) still reach generated C# as live code, and the
contract name is also used unsanitised as the output file path. The generator does not touch key
material, but its output is compiled into consumers' applications, so this is a code-injection path for a
tampered spec (`RISK-008` / `RISK-019`). Verdict: the SDK runtime does not put user private keys at risk
beyond the registered inherent and residual risks; the client generator should not be pointed at an
untrusted ARC56/ARC32 spec until finding G2 is fixed.

## Findings

### G2 — Client generator: spec-derived identifiers, event signatures and the contract name still reach generated code unescaped — new
- **Severity**: Medium (generator output is compiled into consumers' applications)
- **Confidence**: Confirmed for ARC56 (generator executed on modified copies of
  `test/Arc56/GasStation.arc56.json`; output inspected). Plausible for ARC32 (read, not executed).
- **Status**: New (the previous audit's G1 "Residual" flagged these paths as unverified; this audit verifies them)
- **Location**:
  - Argument name: `ClientGenerator/ABI/ARC56/ClientGeneratorARC56.cs:826,837,866` and the parameter
    helpers at `:1009-1033`. `MethodDescription.SafeIdentifier` (`ABI/ARC4/MethodDescription.cs:387-391`)
    only prefixes `@` when the name is a C# keyword; it does not check that the name is an identifier at all.
    Also `:981,991,1001` (`{...Name}RefIndex`). ARC32 equivalent: `ABI/ARC4/MethodDescription.cs:~356`
    (`{s.arg.Name}`).
  - Event name: `ClientGeneratorARC56.cs:640,650`. The signature is built from `evt.Name`, and only `"` is
    escaped when it is written into a string literal; `\` is not.
  - Contract name: `ClientGeneratorARC56.cs:68` (`className = $"{Contract.Name}Proxy"`) and `:55`
    (`GetOutputFileName` = `Contract.Name + ".cs"`), consumed by `client-generator/Program.cs:~84-86`
    (`opts.Output + "/" + generator.GetOutputFileName()` then `File.WriteAllText`).
- **Description**: The previous fix (G1) closed comment breakout. The same trust problem exists wherever a
  spec string becomes an identifier or literal. Observed outputs (marker `PWNED_MARKER`):
  - arg `name` = `x){ var PWNED_MARKER=1; } void Y(int z` produced the generated line
    `public async Task<bool> UpdateApplication(string x) { var PWNED_MARKER = 1; }`, i.e. a method body
    chosen by the spec author, plus a further injected `var x){ ... }` line in the call path.
  - event `name` = `E\"; public static int PWNED_MARKER = 1; //` produced
    `public const string Signature = "E\\"; public static int PWNED_MARKER = 1; //()";` — a new class member
    with a static initializer, which runs attacker-chosen code when the class is first touched.
  - top-level `name` = `X{} class PWNED_MARKER{ static PWNED_MARKER(){} } class Y` produced an extra type
    with a static constructor in the output.
  - top-level `name` = `../../../escaped` made `GetOutputFileName()` return `../../../escaped.cs`. The CLI then
    writes there (`File.WriteAllText`, read at `Program.cs`, not executed): a write outside `--output` of a
    `.cs` file whose content is the generated source. Impact is limited by the `.cs` suffix and the mostly
    fixed content, but it can overwrite an existing source file of that name in a reachable directory, and
    inside the Docker image the bind-mounted output tree is reachable.
  - Not exploitable (checked): ABI `type` strings are rejected (`The ABI type is not valid ...`) before
    emission, for both method args and struct fields; method names and struct names go through
    `ToPascalCase` (alphanumeric only) and produced no marker.
- **Failure scenario**: A developer generates a client from an ARC56 JSON they obtained from a contract
  repository, package or URL (`--url` is a supported input) that has been tampered with or is malicious. The
  generated file looks like ordinary code, compiles, and the injected static initializer or method body
  runs inside their application (possibly in a signer service holding keys). Needs the developer to
  generate from an untrusted spec and not read the output.
- **Recommendation**: Validate rather than patch each site: (1) make `SafeIdentifier` throw unless
  `SyntaxFacts.IsValidIdentifier(name)` and use it for every spec-derived identifier including the
  `{name}Abi` / `{name}RefIndex` derived forms; (2) run `Contract.Name` through `ToPascalCase` or the same
  validation for the class name and, separately, take `Path.GetFileName` of the output name (and verify the
  resolved path is under `--output`); (3) emit string literals via `SymbolDisplay.FormatLiteral` (or escape
  `\` as well as `"`); (4) add tests that feed hostile values into every spec string field of both ARC32
  and ARC56 and compile the output, extending `MultilineDocCommentTests`; (5) document that specs are
  trusted input, in the README next to the Docker usage.

### C1 (update) — CI/release pipeline: actions SHA-pinned, `algokit` pinned; publish job now read in full
- **Severity**: Low
- **Confidence**: Confirmed (read all workflow files; not executed)
- **Status**: Recurring, largely resolved (`AUDIT-2026-10-19-13228ed.md` C1; commit `ffb6406`)
- **Location**: `.github/workflows/*.yml`, `.github/dependabot.yml`
- **Description**: Every `uses:` in the workflows now carries a commit SHA with the tag in a comment, and
  Dependabot (weekly, github-actions) will propose bumps. `algokit` is pinned to `2.10.2`. `publish-nuget.yml`
  was read in full: `id-token: write` is confined to the `publish` job (`permissions: id-token: write,
  contents: read`, environment `nuget-publish`), the job only downloads the `nupkg` artifact and pushes it,
  and `build-and-test.yml` is `permissions: contents: read`. Remaining weaker points: (a) `algokit`'s
  transitive Python dependencies still resolve at install time, and `pipx install` runs in the same job
  before the artifact upload, so a compromised transitive dependency could in principle alter files on disk
  before upload; the packages are built before that step but uploaded after it (Plausible, not
  demonstrated); (b) `generator_build.yml` still uses old action versions (checkout v3, setup-java v2,
  setup-dotnet v1, now SHA-pinned but old), runs on tag/push, and uploads artifacts only — it does not
  publish; (c) the Docker build uses unpinned base image tags (`mcr.microsoft.com/dotnet/sdk:8.0`,
  `runtime:8.0`; no digests) and `docker/login-action` publishes `scholtz2/dotnet-avm-generated-client`.
  The runtime stage correctly drops to a non-root user (`USER $APP_UID`).
- **Recommendation**: Build the packages in a job with no third-party tooling installed, or compute and
  verify a checksum between the build step and upload; pin Docker base images by digest; consider signing
  the generator image (cosign) and documenting the digest per release.

### F1 (update) — Transient-buffer wiping (N1) and test-key warning (N2): resolved
- **Severity**: Low / Informational
- **Confidence**: Confirmed (diff and surrounding code read)
- **Status**: Resolved since last audit (commit `ffb6406`)
- **Location**: `Algod/Model/Account.cs` (`KeyPairFromSeed`), `Algod/Model/FalconAccount.cs`
  (`SeedFromEntropy`, `DetSignCompressed`), `test/TestData/README.md`, `test/PQSignatureTests.cs`
- **Description**: `KeyPairFromSeed` clears the 32-byte intermediate array in a `finally` (so also when
  validation throws) after `KeyPair` has cloned it. `SeedFromEntropy` clears `input`, which holds the
  mnemonic entropy, in a `finally`; `DetSignCompressed` clears the `sign_dyn` `tmp` FFT buffer in its
  `finally`. A README next to the fixtures and an inline comment at the golden mnemonic state that the
  keys are publicly known and must never be funded. Residual (inherent, `RISK-001`/`RISK-015`):
  BouncyCastle's own temporary key objects and its SHAKE state cannot be wiped from here, and the caller's
  own seed array is the caller's to clear.
- **Recommendation**: None beyond the standing "call `Dispose()`" documentation.

## Recommendations for maintainers

1. Fix G2 (identifier validation, contract-name/path sanitising, full string-literal escaping) and extend
   the hostile-spec tests to every spec string field for ARC32 and ARC56. Until then, state in the README
   and the Docker usage docs that specs must come from a trusted source.
2. Remove `MsgPack.Cli` if confirmed unused (and re-check the Unity ILRepack input).
3. Build release packages before any third-party tooling is installed in the job, or verify a checksum
   across the boundary (C1); pin Docker base images by digest.
4. Standing: Unity live verification, `Newtonsoft.Msgpack` maintenance, Falcon golden vectors as a hard gate
   on BouncyCastle bumps, nuget.org id registration and deprecation of `Algorand4`.
