## Summary

This is a verification-focused audit: every shipped-code change since the previous audit
is part of the same-day remediation of that audit's findings F1/F2 and of the separately
discovered `RISK-017` (det1024 signature divergence). All three fixes were verified in
the code at HEAD, and the new golden-vector test infrastructure (3 algokey-signed
transactions, 50 algokey-generated accounts) was reviewed and executed — PQ fixture
12/12, SerialisationTests 23/23, non-LocalNet unit tests 109/109, all passing. The
critical `RISK-017` fix is sound: signing now reproduces `falcon_det1024_sign_compressed`

(N1: a few transient secret buffers in the new signing path are not wiped; N2: 50 real
mnemonics/private keys are committed as public test vectors) — both Low/Informational.
Verdict: the SDK as of this commit does not put user private keys at risk beyond the
previously registered inherent/residual risks, and is in materially better shape than at
`71d6cfc` (the two-preimage key-leak scenario is closed).

## Findings

### V1 — `RISK-017` fix verified: det1024 signing is now reference-exact and golden-pinned
- **Severity**: Informational (verification of a prior Critical-class issue's fix)
- **Confidence**: Confirmed
- **Status**: Resolved since last audit (fixed in `9c680df`/`727f7f7`, this cycle)
- **Location**: `dotnet-algorand-sdk/Algod/Model/FalconAccount.cs:186-269`
  (`SignPQRawBytes` → `DetSignCompressed`), `test/PQSignatureTests.cs`
  (`DetSignaturesAreBitCompatibleWithAlgokey`), `test/TestData/algokey-pq-signed-*.stxn`.
- **Description**: The previous implementation drove BouncyCastle's *public*
  `FalconSigner` with a deterministic `SecureRandom` shim; empirically its output was
  valid but not byte-identical to go-algorand's det1024 signer, which under the
  fixed-salt scheme is key-recovery-grade leakage if the same (key, message) is signed
  by both implementations (`RISK-017`). The replacement was traced line-by-line against
  the reference flow: detrng = SHAKE256(logn ‖ privkey ‖ msg); hash-to-point over
  SHAKE256(fixed-salt ‖ msg); `trim_i8_decode` of f/g/F with a total-length check
  (`u != 2305` hard-fails); `complete_private` for G; BC's internal `FalconSign.sign_dyn`
  seeded directly from the det-RNG SHAKE (bypassing the divergent public wrapper's
  48-byte-reseed behavior); `comp_encode` for the compressed s2. The old
  `RepackToUnsalted` salt-check became unnecessary (the salt is now constructed, not
  sampled) and was removed along with `DetSigningRandom`. The guarantee has moved from
  a runtime format check to something strictly stronger: three full signed transactions
  produced by `algokey pq sign` 5.0.0 are committed as golden vectors and the test
  asserts byte-equality of both the signature and the entire canonical msgpack encoding.
  A 50-account keygen/mnemonic dataset test (`AlgokeyGeneratedDatasetOf50AccountsMatches`)
  pins derivation breadth beyond the previous single golden account. All executed in
  this audit: 12/12 passing.
- **Recommendation**: None. Recorded as the new verified baseline for future audits.

### N1 — A few transient secret buffers in the new signing path are not wiped
- **Severity**: Low
- **Confidence**: Confirmed
- **Status**: New (residual of the F2/RISK-017 remediation, same best-effort class as
  `RISK-015`'s recorded caveats)
- **Location**: `dotnet-algorand-sdk/Algod/Model/FalconAccount.cs:242` (`tmp`, a
  10×1024-element `FalconFPR` array that `sign_dyn` fills with the expanded secret basis
  in FFT form — not cleared after use), `:213-217` (`detrng`, a BC-internal SHAKE256
  object that has absorbed the full private key — its state cannot be cleared through
  reflection-invoked public surface), and `:155-163` (`SeedFromEntropy`'s `input` buffer
  containing the mnemonic entropy is not cleared before return; the derived seed itself
  *is* cleared by the caller).
- **Description**: The remediated signing path wipes `f`/`g`/`F`/`G` in a `finally`
  block, but `sign_dyn`'s working buffer `tmp` holds FFT-domain representations of the
  same secret basis for the duration of the call and is left to the GC uncleaned, as is
  the SHAKE state keyed on the private key and the 37-byte seed-derivation input. This
  is squarely within the residual-caveat territory already recorded under `RISK-015`
  ("BouncyCastle's own per-signature internal copies can't be cleared from here") and a
  memory-read attacker is largely out of scope per `RISK-007` — but `tmp` and `input`
  are SDK-allocated arrays the SDK *could* clear, unlike BC's internals, so the gap is
  narrower than it needs to be.
- **Failure scenario**: Same as `RISK-015`'s: a heap dump of a long-running signer
  captures FFT-domain basis coefficients from a recent signature; recovering f/g from
  the FFT representation is trivial (it's an invertible transform), so `tmp` is as
  sensitive as the key itself while it lingers.
- **Recommendation**: Add `Array.Clear(tmp)`-equivalent to the `finally` block (it's an
  `Array` of a reflected value type — `Array.Clear(tmp, 0, tmp.Length)` works) and clear
  `input` in `SeedFromEntropy` before returning. The SHAKE-state residual is not
  addressable without further BC-internal poking and can stay a documented caveat.

### N2 — 50 real mnemonics/private keys committed as public test vectors
- **Severity**: Informational
- **Confidence**: Confirmed
- **Status**: New
- **Location**: `test/TestData/algokey-pq-accounts.json` (50 mnemonics + raw key pairs),
  `test/PQSignatureTests.cs` (`AlgokeyMnemonic` golden account).
- **Description**: The interop dataset necessarily commits complete, working Falcon-1024
  mnemonics and private keys to a public repository. This is standard, legitimate
  practice for golden-vector testing (go-algorand and every major SDK do the same), and
  the keys have no funds and no on-chain existence. The only risk is human: these
  addresses must never be funded or reused (anything sent to them is takeable by anyone,
  and a developer copy-pasting a "working mnemonic" from test data into an example or
  prototype would be building on a publicly known key). This is a bounded variant of
  `RISK-005`.
- **Failure scenario**: Someone funds one of the committed addresses (by mistake or by
  copying test data into real code); anyone watching the repo can sweep it.
- **Recommendation**: Optionally add a one-line "test vectors — publicly known keys,
  never fund" comment at the top of the JSON or in the fixture; no code change needed.

### N3 — Reflection coupling to BouncyCastle internals has widened from keygen to signing
- **Severity**: Low (functional/supply-chain-adjacent — same class as prior F4)
- **Confidence**: Confirmed
- **Status**: Recurring (extends `AUDIT-2026-08-12-71d6cfc.md` F4 / `RISK-016`)
- **Location**: `dotnet-algorand-sdk/Algod/Model/FalconAccount.cs:373-429`
  (`FalconReflection` — now also binds `FalconSign.sign_dyn`, `FalconCodec.trim_i8_decode`
  /`comp_encode`, `FalconVrfy.complete_private`, `FalconCommon.hash_to_point_vartime`,
  and the `FalconFPR` type).
- **Description**: The `RISK-017` fix *requires* driving BC's internal signer, so the
  reflection surface tracked by `RISK-016` roughly doubled and now covers the hot signing
  path, not just keygen/recovery. The mitigations scale with it: every lookup fail-fasts
  with a clear `NotSupportedException`, the version is pinned, the csproj comment now
  documents that signature bit-identity is a *security* requirement (not cosmetics), and
  the golden gate grew from 2 to 4 named tests that run in the default unit-test pass.
  A BC upgrade that changes internal behavior shape-compatibly would now be caught by
  `DetSignaturesAreBitCompatibleWithAlgokey` before it could ship divergent signatures.
- **Recommendation**: Already-recorded `RISK-016` guidance stands (golden tests are a
  mandatory gate on any BC bump). Longer-term, an upstream BouncyCastle det1024 API or
  a vendored, non-reflective port would remove the coupling; worth an issue, not urgent.
