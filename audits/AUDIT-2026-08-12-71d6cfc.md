# Security Audit — dotnet-algorand-sdk — 2026-08-12

Audited commit: `71d6cfcb93f1876c6ba824ff1b9126d694131558`
Auditor: AI agent (Claude) per `audits/AUDITS-INSTRUCTIONS.md`
Previous audit: `audits/AUDIT-2026-07-18.md` (commit `659abda`)

## Summary

The dominant change since the last audit is an entirely **new key-generation and signing
path**: post-quantum Falcon-1024 support (`FalconAccount`, `PQSignature`, `SignPQ`,
targeting algod 5.0.0 / consensus v42), plus the package rename `Algorand4` →
`Algorand5`. The Falcon path was traced end-to-end: key generation uses BouncyCastle's
CSPRNG-seeded `SecureRandom`, signing is fully offline, the deterministic-signing
`SecureRandom` shim is faithful to the det1024 profile and does not weaken nonce
handling, and no key material is attached to any network request. Two real findings:
the new `FalconKeyInteropExample` **re-introduces the print-a-mnemonic-to-console
anti-pattern** that was removed under `RISK-010` last month (F1), and `FalconAccount`
holds its private key as plain, publicly-gettable, never-cleared `byte[]`s — without the
`IDisposable` best-effort wiping that `Account`/`KeyPair` gained under `RISK-001` (F2).
Neither is a remote-exploitation risk. All prior mitigations (ApiException redaction,
BouncyCastle NuGet pin, CSPRNG asset-hash) were re-verified as intact. Overall verdict:
the SDK as of this commit does not put user private keys at materially greater risk than
the last audit found, with the two findings above recommended for fixes.

## Findings

### F1 — New official example prints a generated mnemonic to the console (RISK-010 pattern re-introduced)
- **Severity**: Medium
- **Confidence**: Confirmed
- **Status**: Recurring — same anti-pattern as `AUDIT-2026-07-16b.md` finding E1 /
  `RISK-010`, fixed then in `OfflineSigningExample.cs`, now re-introduced in a new file.
- **Location**: `sdk-examples/FalconKeyInteropExample.cs:51` —
  `Console.WriteLine($"  mnemonic: {mnemonic}");` — and again at line 54, where the
  mnemonic is interpolated into a printed `algokey pq import -m "..."` command line.
- **Description**: The example generates a fresh Falcon-1024 account and prints its full
  25-word mnemonic to stdout twice. The account is created in-process and unfunded, so
  the example itself exposes nothing of value — but this is official, copy-paste-shaped
  sample code, and the previous audit cycle established the policy that samples must
  never model printing a mnemonic (the identical construct was deliberately removed from
  `OfflineSigningExample.cs` and recorded as `RISK-010`). A developer adapting this
  interop/backup flow for a real account will send the mnemonic to terminal scrollback,
  CI logs, or captured console output. The mitigating nuance versus the 2026-07-16
  occurrence: this example's entire subject is backup/recovery interop, so *some*
  handling of the mnemonic is inherent to what it demonstrates — but displaying it via
  `Console.WriteLine` is not the only way to demonstrate it (the round-trip check at
  line 58 already proves recovery without printing).
- **Failure scenario**: A developer copies the export flow into a tool that provisions
  real PQ accounts; the mnemonic of a funded account lands in a CI log or a
  log-aggregation service; anyone with read access to that sink can reconstruct the key
  with `FalconAccount.FromMnemonic` and drain the account.
- **Recommendation**: Replace both `Console.WriteLine`s with the same approach used in
  the `OfflineSigningExample` fix — keep the mnemonic in a local variable, print a
  placeholder/comment directing the reader to persist it via a secure channel, and keep
  the round-trip verification (which needs no printing). Update the printed `algokey`
  command to use a `<mnemonic>` placeholder.

### F2 — `FalconAccount` key material is plain, publicly-gettable, never-cleared `byte[]`
- **Severity**: Low
- **Confidence**: Confirmed
- **Status**: New (extends the previously-recorded `RISK-001` concern to the new PQ path)
- **Location**: `dotnet-algorand-sdk/Algod/Model/FalconAccount.cs:51` (`public byte[]
  PrivateKey { get; }`), `:59` (`private readonly byte[] entropy`), and
  `:175-181` (`SignPQRawBytes` — LINQ `Skip/Take/ToArray` chains that create four
  additional transient heap copies of private-key components per signature, none of
  which are cleared).
- **Description**: When `Account`/`KeyPair` were remediated under `RISK-001`, they gained
  `IDisposable` with best-effort `Array.Clear` wiping. The new `FalconAccount` has none
  of that: the 2305-byte private key and the 32-byte mnemonic entropy live as ordinary
  managed arrays for the object's whole lifetime, `PrivateKey` is a public getter
  returning the *actual* internal array (a caller — or any code handed the account —
  can read or even mutate it), and every signature materializes several uncleared
  copies of `f`/`g`/`F` on the GC heap. Additionally, BouncyCastle's
  `FalconPrivateKeyParameters` instances created per-signature hold their own copies.
  This is the same CLR-inherent, best-effort-only territory as `RISK-001` (a memory-read
  attacker is already largely out of scope per `RISK-007`), so severity is Low — but the
  asymmetry with the classic `Account` is a real regression in defense-in-depth for
  anyone adopting the PQ path, and PQ keys are exactly the keys users intend to be
  long-lived.
- **Failure scenario**: A long-running signer service holds a `FalconAccount`; a heap
  dump taken for debugging (or exfiltrated by malware) is later shared/leaked; the
  2305-byte `0x5A`-headed private key is trivially carveable from the dump by its size
  and header byte, with no wiping ever having been attempted.
- **Recommendation**: Mirror the `RISK-001` remediation: implement `IDisposable` on
  `FalconAccount` (clear `PrivateKey`, `entropy`, and drop references), have
  `PublicKey`/`PrivateKey` getters return defensive copies (or document that they
  return live buffers), and clear the transient `skBody`/`f`/`g`/`F` arrays in
  `SignPQRawBytes` after the signature is produced.

### F3 — Falcon-1024 signing path verified sound (positive finding, no action)
- **Severity**: Informational
- **Confidence**: Confirmed
- **Status**: New
- **Location**: `FalconAccount.cs:197-202` (RNG), `:309-335` (`DetSigningRandom`),
  `PQSignature.cs:159-172` (`RepackToUnsalted`), `Transaction.cs:256-264` (`SignPQ`).
- **Description**: The new key/signing path was traced end-to-end and holds up:
  - **RNG**: fresh accounts seed from `new SecureRandom()` (BouncyCastle's
    CSPRNG-backed default — not `System.Random` or time-seeded).
  - **Deterministic signing**: `DetSigningRandom` implements the falcon_det1024 profile
    — the first 40-byte draw (the nonce) returns the *fixed* versioned salt and all
    subsequent draws come from SHAKE256(logn ‖ privateKey ‖ message). Determinism here
    is by upstream design (go-algorand's verifier re-adds the same fixed salt), and it
    *removes* the classic randomness-failure class rather than adding one; the sampler
    stream being keyed on the private key + message matches the reference
    `falcon_det1024_sign_compressed`. `RepackToUnsalted` hard-fails if the signature
    was not produced over the expected fixed salt, so a BouncyCastle behavior change
    cannot silently produce a differently-salted signature.
  - **Offline**: `SignPQ`/`SignPQRawBytes`/`LogicsigSignature.SignPQ` make no network
    calls; only the signed transaction blob (public by design) leaves the process.
  - **Address derivation**: `FindCanonicalSalt`'s Edwards25519 rejection loop mirrors
    go-algorand's admission rule; golden-vector tests (`test/PQSignatureTests.cs`) pin
    address and mnemonic derivation against `algokey pq` output.
- **Recommendation**: None — recorded so future audits can diff against a verified
  baseline instead of re-deriving.

### F4 — Falcon keygen drives BouncyCastle *internals* via reflection (functional fragility, not a security flaw)
- **Severity**: Low (functional/supply-chain-adjacent, no key-security impact today)
- **Confidence**: Confirmed
- **Status**: New
- **Location**: `FalconAccount.cs:211-300` (`ReferenceKeygen`, `KeygenReflection`).
- **Description**: To be byte-identical with algokey's deterministic reference keygen,
  the SDK invokes BouncyCastle's non-public `SHAKE256`/`FalconKeygen`/`FalconCodec`
  types by reflection. This is done carefully — every lookup fails fast with a clear
  `NotSupportedException` if BC's internals change shape, and BC is pinned at 2.6.2 —
  but it creates a hidden coupling: **upgrading BouncyCastle (e.g. for a future CVE,
  the exact scenario `RISK-002` exists for) can now break Falcon key
  generation/recovery** and, worse than breaking loudly, could in principle change
  derivation silently if BC ever altered internal *behavior* without altering member
  shapes. The golden-vector tests (`AddressDerivationMatchesAlgokey`,
  `MnemonicRecoveryMatchesAlgokey`) are the real guardrail: any behavioral drift fails
  them.
- **Failure scenario**: A future maintainer bumps BouncyCastle to patch a CVE; the
  reflection cache throws (best case — Falcon accounts stop working until fixed) or,
  hypothetically, a shape-compatible behavioral change makes `FromMnemonic` derive a
  *different* key pair than the one a user backed up — a recovery failure, not a theft.
- **Recommendation**: Keep the golden-vector tests mandatory in CI for any BC version
  bump (they already run in the plain unit-test pass — good); add a one-line note to
  the csproj comment pinning BC 2.6.2 that `FalconAccount.KeygenReflection` is an
  additional reason the pin is load-bearing.

### F5 — Package rename to `Algorand5`: register the new nuget.org IDs promptly
- **Severity**: Informational
- **Confidence**: Confirmed
- **Status**: New
- **Location**: `dotnet-algorand-sdk/dotnet-algorand-sdk.csproj` (`PackageId`
  `Algorand5`, version `5.0.0.*`), `Algorand5_Unity.nuspec`,
  `.github/workflows/publish-nuget.yml`.
- **Description**: The package ids changed from `Algorand4`/`Algorand4_Unity` to
  `Algorand5`/`Algorand5_Unity`, and the publish workflow's Trusted Publishing setup
  notes correctly instruct creating policies for the new ids. Until the first publish
  (or id reservation) actually happens on nuget.org, the new names are claimable by
  anyone — a package-id squatting window. Discontinuity also means consumers of
  `Algorand4` won't receive `Algorand5` updates automatically; a final `Algorand4`
  release note/deprecation pointing at `Algorand5` would prevent stragglers from
  sitting on an unmaintained id (or worse, trusting a future squatter's `Algorand4`
  upload if ownership ever lapsed).
- **Recommendation**: Publish (or reserve) `Algorand5` and `Algorand5_Unity` on
  nuget.org as soon as practical under the existing owner account; mark the last
  `Algorand4`/`Algorand4_Unity` versions as legacy/deprecated with a pointer to the
  new ids.

## Recommendations for maintainers

1. **Fix Finding F1** (`FalconKeyInteropExample.cs:51,54`): stop printing the generated
   mnemonic; use the same redaction approach as the earlier `OfflineSigningExample`
   fix. Trivial, and it restores the "samples never print mnemonics" policy.
2. **Fix Finding F2**: add `IDisposable` + best-effort wiping and defensive-copy
   getters to `FalconAccount`, matching the `RISK-001` remediation on
   `Account`/`KeyPair`.
3. Register/publish the `Algorand5` and `Algorand5_Unity` nuget.org ids promptly and
   deprecate the `Algorand4` ids with a pointer (Finding F5).
4. Treat the Falcon golden-vector tests as a mandatory gate on any future
   BouncyCastle version bump (Finding F4 / `RISK-016`).
5. Standing items from prior audits remain: periodically re-check `Newtonsoft.Msgpack`
   maintenance status (`RISK-012`); defer live Unity-runtime and gossip-live-network
   verification to an environment with those prerequisites.
